# PackBot Handoff

## Что такое PackBot

PackBot — это служебный Telegram-бот, интегрированный с бэкендом ForzaDJ. Он предназначен для администраторов (superadmins) и позволяет быстро создавать редакционные подборки (паки) треков прямо из мессенджера Telegram. 

Бот использует API-эндпоинты основного Next.js приложения для получения метаданных (жанров), поиска треков по каталогу и создания сущностей в базе данных.

## Бизнес-логика

Полный пользовательский сценарий:
1. **Telegram:** Пользователь (админ) вызывает команду `/start` или нажимает кнопку **Create Pack**.
2. **Выбор параметров:**
   - Выбор жанра (одиночный выбор).
   - Выбор настроения/вайба (Mood).
   - Выбор версий трека (мультивыбор: Original, Extended и т.д.).
   - Выбор количества треков (5, 10 или 20; максимум бизнес-логики).
3. **Подбор треков (Поиск):** Бот запрашивает API, который использует `catalogQueue` для формирования уникального, отфильтрованного и перемешанного (shuffle) пула треков из базы данных.
4. **Превью:** Бот присылает список найденных треков в текстовом виде. Администратор подтверждает список (Approve) или пересобирает (Regenerate).
5. **Обложка:** Администратор загружает JPEG/PNG картинку прямо в чат Telegram. Бот скачивает её через Telegram API.
6. **Создание пака на сайте (Публикация):** Бот отправляет данные пака, список `versionId` треков и Blob обложки на внутренний API `create`, который загружает обложку в S3/Supabase Storage, создает пак (Collection) и возвращает ссылку на готовый пак на сайте.

## Архитектура

PackBot состоит из двух изолированных, но связанных частей:
1. **Скрипт бота (Node.js)**: Работает как самостоятельный фоновый процесс. Опрашивает Telegram, хранит состояние (FSM) и делает HTTP-запросы к основному сайту.
2. **API Routes (Next.js)**: Находятся в основном проекте ForzaDJ, принимают запросы от скрипта бота, общаются с базой данных (Prisma) и возвращают JSON ответы.

### Какие файлы участвуют в работе бота
- `scripts/pack-bot.mjs` — основной исполняемый файл Telegram-бота.
- `src/app/api/bot/packs/meta/route.ts` — API-эндпоинт для получения справочников (жанры, муды).
- `src/app/api/bot/packs/search/route.ts` — API-эндпоинт для поиска пула треков.
- `src/app/api/bot/packs/create/route.ts` — API-эндпоинт для сохранения пака в БД.
- `src/server/repositories/collection.repository.ts` — репозиторий паков (в частности, методы `createPack`, `addItem`, `updatePackMeta`, `setPackVisibility`).
- `src/server/repositories/catalog.repository.ts` — репозиторий треков (метод `orderedQueue`).
- `src/server/services/search.service.ts` — сервис поиска (метод `catalogQueue`).

### Prisma модели и таблицы БД
- `Collection`: для хранения самого пака (тип `EDITORIAL`, статус `PUBLIC`).
- `CollectionItem`: связующая таблица для добавления треков (конкретных версий `TrackVersion`) в `Collection`.
- `Genre` / `Track` / `TrackVersion`: таблицы каталога, по которым осуществляется фильтрация.

## FSM (State Machine)

Вся логика диалога с ботом реализована через In-Memory `Map`, хранящий состояние пользователя (FSM). 

Шаги и переходы:
- **`IDLE`**: Начальное состояние, ожидание нажатия `action:create`.
- **`SELECT_GENRE`**: Бот вывел клавиатуру жанров. Ожидает `callback_query` с `genre:<slug>`.
- **`SELECT_MOOD`**: Бот вывел клавиатуру мудов. Ожидает `callback_query` с `mood:<slug>`.
- **`SELECT_VERSION`**: Мультивыбор версий. При клике на `version:<slug>` состояние переключается (`☑`/`☐`). При нажатии на `action:continue_version` — переход к следующему шагу.
- **`SELECT_COUNT`**: Бот вывел кнопки 5, 10, 20. Ожидает `callback_query` с `count:<number>`.
- **`PREVIEW`**: Ожидает `action:approve` (переход к обложке) или `action:regenerate` (повторный запрос к `/search`).
- **`WAIT_ARTWORK`**: Ожидает входящее сообщение типа `photo`.
- **`DONE`**: Пак опубликован, сессия удаляется.

## Telegram Integration

- **Библиотека**: Для простоты и минимализма бот использует прямые HTTP-запросы (Fetch) к `api.telegram.org` без сторонних фреймворков (типа Telegraf), реализуя механизм **Long Polling** в бесконечном цикле.
- **Методы Telegram API**: `getUpdates`, `sendMessage`, `editMessageText`, `answerCallbackQuery`, `getFile`.
- **Webhooks**: В текущей реализации отключены/не используются для PackBot. Бот работает в push/pull polling режиме через `scripts/pack-bot.mjs`. (На сайте есть `api/telegram/webhook`, но он, вероятно, используется для другой функциональности).
- **Env-переменные**:
  - `TELEGRAM_BOT_TOKEN` — токен бота от BotFather.
  - `API_URL` — базовый URL сайта (например, `http://127.0.0.1:3000`).
  - `BOT_SECRET` — пароль/секрет для авторизации HTTP-запросов между скриптом и API сайта (заголовок `x-bot-secret`).
  - `SUPERADMIN_IDS` — ID администраторов (comma-separated), которым разрешено пользоваться ботом.

## API Endpoints

Все эндпоинты защищены проверкой заголовка `x-bot-secret`.

### `GET /api/bot/packs/meta`
- **Назначение**: Отдает списки жанров, мудов и типов релизов для шагов бота.
- **Параметры**: Нет.
- **Ответ**: `{ genres: [...], moods: [...], releaseTypes: [...] }`.

### `GET /api/bot/packs/search`
- **Назначение**: Поиск, фильтрация, дедупликация и перемешивание пула треков.
- **Параметры**:
  - `genre` (string)
  - `mood` (string)
  - `types` (string, comma-separated) — версии треков.
  - `limit` (number) — максимум 20.
- **Ответ**: `{ success: true, count: number, limit: number, items: [ { trackSlug, versionId, artists, title } ] }`.

### `POST /api/bot/packs/create`
- **Назначение**: Сохранение обложки и создание пака в БД.
- **Параметры (FormData)**:
  - `title` (string)
  - `artwork` (File/Blob)
  - `tracks` (string) — JSON массив `versionId`.
  - `ownerId` (string) — Admin ID.
- **Ответ**: `{ success: true, packId, slug, url }`.

## Поиск треков

Поиск работает на базе функции `catalogQueue` (или `catalogRepository.orderedQueue`).
1. Бот передает параметры в `/search`.
2. Эндпоинт разбивает `types` на массив. Если выбрано несколько типов (Original, Remix), он делает отдельные запросы `catalogQueue` для каждого типа, запрашивая по умолчанию до 500 треков.
3. Массивы объединяются в один гигантский пул.
4. Пул проходит **дедупликацию** (уникальность проверяется по `trackSlug`), чтобы в пак не попал один и тот же трек разными версиями.
5. Пул **перемешивается** алгоритмом Fisher-Yates (Shuffle).
6. Массив обрезается (slice) до переданного `limit` (но не больше 20) и отдается боту.

## Создание пака

Эндпоинт `create` выполняет действия в следующем порядке:
1. Валидация входных данных, извлечение картинки (`image/jpeg` или `application/octet-stream`).
2. Определение Storage Bucket и генерация уникального ключа файла `artworkPath`.
3. Загрузка картинки в облачное хранилище (Supabase S3) через `getStorage().put(...)`.
4. Генерация человекочитаемого `slug` (через `slugify` и `nanoid`).
5. Вызов `collectionRepository.createPack(...)`. Эта операция жестко прописывает `type: "EDITORIAL"` и `visibility: "PRIVATE"`.
6. В цикле (for..of) добавление каждого трека через `collectionRepository.addItem(...)`.
7. Обновление метаданных пака (добавление `coverKey` и `trackCount`) через `updatePackMeta`.
8. Публикация пака: вызов `setPackVisibility` с `visibility: "PUBLIC"`.
9. Очистка кэша Next.js (`revalidateTag`, `revalidatePath`).

## Известные проблемы

В ходе E2E тестирования обнаружены следующие нюансы/ограничения, о которых необходимо знать:

1. **Проблема инвалидации кэша (Next.js Cache Invalidation)**:
   Если запустить `scripts/pack-bot.mjs` локально, но при этом передать `API_URL="http://127.0.0.1:3000"`, то API бота очистит ISR/Data Cache только на **локальном dev-сервере**. При этом URL, который возвращает бот, может быть сгенерирован на основе продакшн `NEXT_PUBLIC_APP_URL="https://forzadj.ru"`.
   *Симптом:* Пользователь переходит по ссылке `forzadj.ru/packs/...` и получает `404 Not Found`, так как продакшн-сервер Vercel не сбрасывал свой кэш.
   *Воркэраунд:* Тестировать паки локально (`localhost:3000/packs/...`) либо перенаправить бота на продакшн API (`API_URL="https://forzadj.ru"`).

2. **Малое количество треков (Search Pool Issue)**:
   При выборе узкоспециализированных фильтров (например: Tech House + Prime Time + Original) может найтись всего 5 треков, даже если пользователь запросил 20. 
   *Причина:* `catalogQueue` (через Prisma) жестко фильтрует базу только по опубликованным трекам, которые точно соответствуют пересечению **всех** выбранных категорий. Если на живом сайте в каталоге визуально больше треков — вероятно, локальная БД синхронизирована не полностью (или фильтр `mood` на фронтенде работает иначе).

3. **Сбой при `npm run build` во время `next dev`**:
   Запуск `npm run build` очищает и перезаписывает директорию `.next`. Если в этот момент работает `npm run dev` (к которому обращается бот), dev-сервер упадет с ошибкой `ENOENT: no such file or directory` (Build Manifest Error) и начнет отвечать `500 Internal Server Error` боту.

## Деплой

Бот не зависит от Vercel. Его нужно крутить как фоновый worker.

### Как запускать локально (для тестов)
1. Убедиться, что запущен Next.js сервер: `npm run dev`.
2. Настроить `.env`:
   ```bash
   TELEGRAM_BOT_TOKEN="твой_токен"
   API_URL="http://127.0.0.1:3000"
   BOT_SECRET="любой_сложный_пароль"
   ```
3. Запустить бота в отдельном терминале: `node scripts/pack-bot.mjs`.

### Как запускать на VPS (Production)
1. Убедиться, что `API_URL` указывает на реальный домен (например, `https://forzadj.ru` или внутренний IP бэкенда).
2. Запустить скрипт через **PM2** (менеджер процессов Node.js), чтобы он не умирал при закрытии консоли и перезагрузке сервера:
   ```bash
   # Установить PM2 если нет
   npm install -g pm2
   
   # Запустить
   pm2 start scripts/pack-bot.mjs --name "forzadj-packbot"
   
   # Сохранить автозапуск
   pm2 save
   pm2 startup
   ```

## Аудит 2026-08-16 (результаты и правки)

Проведён сквозной аудит `Telegram → FSM → API → Search → Prisma → Collection → Frontend`
с фактической проверкой по боевой БД (423 опубликованных трека).

### Факты, подтверждённые SQL
- **312 из 423 треков имеют `mood = null`** (PRIME_TIME=85, WARM_UP=15, AFTER_PARTY=11).
  Комбинация из handoff `tech-house + PRIME_TIME + ORIGINAL` = **0 треков** в каталоге;
  без mood: `tech-house + ORIGINAL` = 11, `tech-house` = 67.
- **Все 423 трека имеют ровно один тип опубликованной версии** (0 треков с несколькими
  типами версий).

### Разбор известных проблем
1. **«Мало треков» — это НЕ баг, а разреженность данных.** Бот использует ту же функцию
   `trackWhere`, что и каталог сайта, поэтому по одинаковым фильтрам счётчики совпадают
   с витриной. «Меньше, чем запросили» возникает, когда в каталоге столько и есть
   (в основном из-за `mood`). Ослаблять фильтры нельзя — иначе результат перестанет
   соответствовать каталогу. Живой тест: `search?genre=tech-house&types=ORIGINAL&limit=10`
   вернул 10 (пул = 11). ✅
2. **«Пак пропадает после публикации» — исправлено.** В `create/route.ts` обложка грузилась
   в Storage **до** установки `PUBLIC`. Любой сбой загрузки → внешний `catch` → 500, пак
   оставался `PRIVATE` (создан, с треками, но не на витрине). Теперь загрузка обложки
   обёрнута в собственный `try/catch` и **не срывает публикацию** (пак публикуется без
   обложки, ошибка логируется).
3. **«Пак есть, но треков нет» — добавлена защита.** `create/route.ts` теперь отклоняет
   пустой список треков (400) и дедуплицирует `versionId`.
4. **Связка Collection ↔ CollectionItems — корректна.** `addItem` идемпотентен по составному
   ключу `(collectionId, versionId)`; публикация/витрина скоупятся `type=EDITORIAL`,
   `visibility=PUBLIC`, `deletedAt=null`.
6. **Фильтры реально участвуют.** genre (slug→ids, с поджанрами), mood (enum), type (enum),
   мультивыбор версий (per-type queue + dedup) — всё уходит в `trackWhere`. Подтверждено
   живыми запросами и SQL.

### Внесённые изменения
- `src/server/repositories/catalog.repository.ts` — `orderedQueue`: при заданном фильтре
  `type` в очередь выбирается версия **именно этого типа** (fallback к прежней логике,
  если такой версии нет). На текущих данных ничего не меняет (проверено: 0 расхождений),
  но гарантирует корректность, если появятся треки с несколькими типами версий.
- `src/app/api/bot/packs/create/route.ts` — (а) загрузка обложки некритична для публикации;
  (б) серверный лимит ≤20 треков и запрет пустого пака; (в) `revalidatePath("/packs")`
  для мгновенного обновления публичной витрины.

### 🔴 Корневая причина витрины/публикации: STORAGE_DRIVER указывает на отключённый Supabase
Storage мигрировал на **Cloudflare R2**, но локальный `.env` всё ещё содержит
`STORAGE_DRIVER="supabase"` **и не содержит R2-переменных**. Supabase-проект ограничен по
квотам (`exceed_egress_quota`, `exceed_storage_size_quota`), поэтому:
- `createSignedDownloadUrl` бросал исключение → `packCoverUrl` пробрасывал → **`/packs` и
  главная `/` падали в 500** для любого пака с обложкой;
- загрузка обложки при публикации падала → (до фикса) пак застревал `PRIVATE` («после
  публикации пак отсутствует на сайте»).

Подтверждено логами dev-сервера (`SupabaseStorageAdapter.createSignedDownloadUrl failed:
... exceed_egress_quota ...`).

**Требуется (действие владельца, секреты не редактировались автоматически):**
в `.env` (локально и на Timeweb VPS) задать:
```bash
STORAGE_DRIVER="r2"
R2_ENDPOINT="https://<account>.r2.cloudflarestorage.com"
R2_BUCKET="<bucket>"
R2_ACCESS_KEY_ID="<key>"
R2_SECRET_ACCESS_KEY="<secret>"
```
Дефолт драйвера в коде уже `r2` (`src/server/storage/index.ts`) — достаточно убрать
устаревший `STORAGE_DRIVER="supabase"` и добавить R2-креды.

Код дополнительно защищён (см. ниже): даже при сбое Storage витрина/главная больше не 500,
а публикация пака не срывается (пак создаётся без обложки).

- `src/server/services/pack.service.ts` — `packCoverUrl` оборачивает подпись обложки в
  `try/catch` → при сбое Storage возвращает `null` (пак без обложки), а не роняет
  страницу в 500.
